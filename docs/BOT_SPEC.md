## 1. Назначение

Два Telegram-бота исполняют роль **продакт-оунеров** двух продуктов
(LT Parsing — краулинг конкурентов; LT Matching — сопоставление товаров и
ценовой индекс) и общаются с Head of Product в групповом чате:

1. **Инициативно** — ежедневный дайджест метрик своего продукта и
   немедленные алерты при деградациях уровня serious/critical.
2. **Реактивно** — ответы на вопросы в режиме живого чата (секунды),
   срезами реальных данных последнего прогона пайплайна.

Боты не «генерируют мнение»: каждая цифра в их ответах читается из
артефактов пайплайна (`data/*.json`), тех же, что видит дашборд
«Кабина пилота» (https://tp9mc.github.io).

## 3. Архитектура исполнения: serverless-вахта

У ботов **нет постоянного сервера**. Аккаунты ботов живут на серверах
Telegram (очередь входящих хранится там до 24 ч); код исполняется на
одноразовых раннерах GitHub Actions. Четыре точки исполнения:

| Воркфлоу | Триггер | Роль |
|---|---|---|
| `realtime-bots.yml` | cron `7,37 * * * *` + ручной | **Основной режим.** «Вахта»: job живёт до 350 мин и непрерывно слушает Telegram (long polling `getUpdates(timeout=45)`, по потоку на бота). Ответы — за 1–3 секунды |
| `pipeline.yml` (шаг PO bots report) | каждые ~3 ч, после прогона | Инициативные сообщения: `send_report --kind auto` → дайджест (раз в день) или алерты (serious/critical) |
| `po-bots.yml` | только ручной | Разовый опрос-резерв (наследие крон-режима). Не запускать при живой вахте |
| `bot-test.yml` | только ручной | Тест связи + полная диагностика (getMe, webhook, содержимое очереди, отправка тестовых сообщений). Принимает опциональный input `chat_id` |

### 3.1. Непрерывность вахты (ключевой механизм)

- Все запуски `realtime-bots` состоят в concurrency-группе `realtime-bots`
  с `cancel-in-progress: false`: одновременно живёт **один** ран, следующий
  стоит в очереди (GitHub держит в очереди максимум один — новые заменяют его).
- Крон дважды в час гарантирует, что очередь не пустеет. Когда активная
  смена завершает свои ~5.5 ч, очередная стартует немедленно —
  зазор передачи составляет секунды.
- **Офсеты** прочитанных апдейтов передаются между сменами через
  `actions/cache` (файл `/tmp/bot-offsets.json`, ключ `bot-offsets-<run_id>`,
  восстановление по префиксу `bot-offsets-`).
- **Холодный старт** (кэш пуст/протух): бот обрабатывает сообщения не старше
  10 минут, более старый хвост пропускает целиком — защита от двойных
  ответов и от «воскрешения» давно прочитанного.
- Подтверждённая живучесть: с 2026-07-10 по 2026-07-29 — **252 смены подряд**
  без вмешательства человека.

### 3.2. Жёсткие ограничения среды (важно при доработках)

1. `getUpdates` Telegram отдаёт **только одному потребителю**; второй
   параллельный получает `409 Conflict`. Поэтому `po-bots`/`bot-test`
   вручную запускать при живой вахте нельзя (bot-test дополнительно
   снимает webhook, если тот был установлен и блокировал polling).
2. Лимит job hosted-раннера — 6 ч; смена рассчитана на 335 мин + буфер.
3. GitHub отключает cron-расписания после 60 дней без активности
   пользователей в репозитории; активность пайплайна это компенсирует,
   но при «заморозке» проекта вахту придётся оживить кнопкой Run workflow.
4. Крон GitHub исполняется с плавающей задержкой (минуты–десятки минут) —
   архитектура это учитывает (очередь смен, а не точные тики).

## 4. Поток данных

```
Telegram (очередь апдейтов ботов, TTL 24 ч)
   ▲ sendMessage (HTML)            │ getUpdates (long poll 45 c)
   │                               ▼
GitHub Actions: realtime-bots (вахта, 2 потока — по боту)
   │  чтение срезов                │ офсеты
   ▼                               ▼
data/*.json (артефакты пайплайна) actions/cache (bot-offsets.json)
   ▲
pipeline.yml (каждые ~3 ч): прогон → send_report (дайджест/алерты)
                                   → коммит data/ (включая state.json)
```

## 5. Инициативные сообщения

### 5.1. Дневной дайджест (`--kind auto` → digest)
- Отправляется, если `state.last_digest != сегодня (UTC)`; после отправки
  дата фиксируется и коммитится (шаг отчёта выполняется **до** коммита
  данных — порядок важен, см. фикс v1.1).
- Лера: офферы/источники/success rate/свежесть, сигналы рынка
  (изменения цен, новинки/выбытия, OOS), пер-источник строки, риски.
- Марк: вход/пары, авто-мэтч и итоговый match rate, precision/recall/F1,
  очередь валидации, ценовой индекс (покрытие, конкурентоспособность,
  средний разрыв), риски.
- Тренды в скобках: сравнение с прошлым прогоном («↗0.3%, хорошо» /
  «↘0.5%, следим»).

### 5.2. Алерты (`--kind auto` → alerts, когда дайджест уже был)
- Только severity **serious/critical** (warning остаются на дашборде).
- Лера получает алерты продукта parsing; Марк — matching + shared
  (сквозные, например падение покрытия индекса).
- Правила алертов определены в `tools/analytics/aggregate.py` и描аны в
  [METRICS.md](METRICS.md) и руководстве (раздел 05 «Светофор»).

## 6. Реактивные ответы: маршрутизация

Обработчик — `tools/po_bots/bot.py::handle_update` (общий для вахты и
резервного опроса).

1. Сообщения ботов и пустые тексты игнорируются.
2. **Личка** боту → отвечает всегда.
3. **Группа** → бот отвечает, если сообщение адресовано ему:
   - упоминание `@username` или ответ (reply) на его сообщение;
   - имя персоны в тексте («Лера, …», «Марк, …»);
   - /команда без чужого @упоминания (`/status`, `/help`, …) — на «общие»
     команды отвечают **оба** бота, каждый про своё;
   - тематические ключевые слова своего продукта:
     - Лера: парсинг, источник, обкачк-, краулер, свежест-, магазин, капч-;
     - Марк: мэтчинг/матчинг, сопоставл-, очеред-, прайс, индекс,
       precision, recall, валидаци-, цен-.
4. Ни адресата, ни темы → бот молчит (защита от хорового спама).

### 6.1. Команды и темы

| Запрос | Кто отвечает | Содержание ответа |
|---|---|---|
| `/start` | оба | приветствие + краткая справка |
| `/help`, «что ты умеешь» | оба | список тем и команд |
| `/status`, «статус», «как дела», `/digest`, «дайджест/сводка» | оба | полный дайджест своего продукта |
| `/risks`, «риски/проблемы/алерты» | оба | открытые алерты своего продукта |
| `/manual`, «инструкция/руководство/плейбук» | оба | шпаргалка со светофором + ссылка на https://tp9mc.github.io/manual.html |
| «lamoda», «головная» | оба | статус связи с www.lamoda.ru (из `data/shared/hq.json`) |
| «источники», «свежесть», «покрытие», «качество данных» | Лера | срезы обкачки |
| «очередь/валидация», «качество/precision/recall», «прайс-индекс», «цены конкурентов» | Марк | срезы мэтчинга и цен; для прайс-индекса — включая топ-отклонение с ценами |
| прочий адресованный текст | адресат | вежливый fallback со списком тем |

Формат всех сообщений: Telegram HTML (`parse_mode=HTML`), подпись персоны
курсивом, без предпросмотра ссылок.

## 8. Конфигурация и «ручки»

| Параметр | Где | Значение/эффект |
|---|---|---|
| Персоны, эмодзи, подписи | `bot.py::PRODUCTS` | имена/тон ботов |
| Ключевые слова адресации | `bot.py::is_addressed` | кто на что реагирует |
| Длительность смены | `realtime-bots.yml` (`--minutes 335`, timeout 350) | ↑ дольше смена — реже ротация |
| Частота подстраховки | cron `7,37 * * * *` | плотность очереди смен |
| Окно холодного старта | `realtime.py::COLD_START_WINDOW_S=600` | сколько «догонять» после разрыва |
| Long-poll таймаут | `realtime.py` (`timeout=45`) | латентность/частота запросов |
| Правила алертов | `tools/analytics/aggregate.py` | когда боты бьют тревогу |

Изменение = обычный коммит в `main`; вахта подхватит код со следующей смены
(или перезапустить ран вручную).

## 9. Эксплуатация и диагностика

- **Живой лог вахты**: Actions → realtime-bots → активный ран → job `shift`
  → шаг *Stand watch*: `«product: @username на вахте, offset=…»`,
  `«product: ответил на „…“»`, ошибки getUpdates.
- **Норма в списке ранов**: один `in progress` (текущая смена) + периодически
  `queued`/`cancelled` pending (ротация очереди) — это штатно.
- **Полная диагностика одним кликом**: bot-test (Run workflow) — печатает
  getMe/webhook/очередь по-русски и шлёт тестовые сообщения в чат.
- **Плейбук «боты молчат»**: руководство пилота, раздел 06, плейбук №8
  (проверка вахты → адресация → секреты → privacy → 409).
- Стоимость: $0 (Actions для публичных репозиториев бесплатны).

## 10. Безопасность

- Токены ботов только в GitHub Actions Secrets; в логах маскируются.
  После `/revoke` в BotFather — обновить секрет.
- Логи Actions публичны (репозиторий публичный): печатаются username ботов,
  количество апдейтов и **обрезанный до 60 символов** текст сообщений, на
  которые ответили. Не обсуждать в рабочем чате чувствительное — или
  сделать репозиторий приватным.
- `chat_id` группы хранится в открытом репозитории: сам по себе доступа
  к чату не даёт (нужен токен участника-бота).
- Боты не исполняют команд, меняющих систему: только чтение метрик.

## 11. Известные ограничения

1. Ответ «за секунды» — внутри смены; в момент передачи смены возможна
   пауза в секунды; при полном разрыве (обе смены умерли) — до крон-слота.
2. При холодном старте сообщения старше 10 минут не отвечаются (by design).
3. На общие /команды в группе отвечают оба бота (конвенция Telegram).
4. Знания ботов = последний прогон пайплайна (лаг до ~3 ч по метрикам;
   «живее» только сам рынок между прогонами не наблюдается).
5. Очередь Telegram хранит недоставленное 24 ч: простой дольше суток
   теряет входящие за его пределами.
6. NLU нет — маршрутизация по ключевым словам; вопросы «не по словарю»
   получают fallback-подсказку.

### 12.2. Особенности процесса разработки агентом
- Полный цикл в одной сессии: постановка → архитектура → код → локальные
  прогоны → деплой в `main` → мониторинг боевых ранов → инцидент-дебаг.
- Дебаг «слепых зон»: из песочницы агента закрыты api.telegram.org и
  lamoda.ru, поэтому агент выносил диагностику в логи Actions
  (человекочитаемые строки) и читал их через GitHub API; факты с экрана
  пользователя (скриншоты Telegram/Actions) использовались как данные.
- Найденные и закрытые в процессе дефекты: latin-1 мойибake из-за
  отсутствия charset у локального HTTP-сервера; «идеальные» метрики
  (перекалибровка порогов и усложнение рынка); TIME_WAIT порта;
  недоставка сообщений, отправленных до входа ботов в группу; порядок
  шагов workflow (digest-фикс v1.1).
- Каждый коммит агента помечен трейлером `Co-Authored-By: Claude` и
  ссылкой `Claude-Session` — по ним восстанавливается провенанс изменений.
- Как вносить изменения дальше: править код обычными коммитами в `main`
  (раздел 8) — или продолжить сессию Claude Code; контекст проекта
  зафиксирован в `CLAUDE.md`, этой спеке, ARCHITECTURE.md и руководстве.
